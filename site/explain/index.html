Explanation · one rendered frame

From JavaScript to pixels.

The browser does not “run a shader” by itself. A frame appears only after several contracts line up: device capabilities, resource layouts, WGSL entry points, render state, encoded commands, and a presentable surface.

Pipeline map

Six boundaries worth naming

  1. 01

    Adapter → device

    The adapter describes a candidate GPU implementation and its limits. The device is the logical GPU connection used to create resources and submit work.

  2. 02

    Canvas → surface format

    The WebGPU canvas context is configured with a device and preferred texture format. Each frame supplies a texture that can become a color attachment.

  3. 03

    WGSL → shader module

    WGSL source defines typed entry points. Shader Lab asks the browser for compilation diagnostics before replacing the currently working pipeline.

  4. 04

    Bindings → pipeline layout

    The uniform buffer is not discovered magically. A bind-group layout declares which resource exists at binding 0 and which shader stages may read it.

  5. 05

    Commands → render pass

    The CPU encodes a pass, selects the pipeline and bind group, and records a draw of three vertices. No vertex buffer is needed for the full-screen triangle because the vertex index generates its positions.

  6. 06

    Queue → presentation

    The command buffer is submitted to the device queue. WebGPU schedules the GPU work, the canvas texture receives the fragment output, and the browser presents it.

CPU side

What changes each frame?

Shader Lab writes eight 32-bit floats into one 32-byte uniform buffer: resolution, elapsed time, animation speed, pointer position, and padding required by the layout.

resolution  vec2<f32>   8 bytes
time        f32          4 bytes
speed       f32          4 bytes
pointer     vec2<f32>   8 bytes
padding     vec2<f32>   8 bytes
                         ────────
                         32 bytes

GPU side

Why only three vertices?

A single oversized triangle covers the viewport. Every covered pixel invokes the fragment shader, so the experiment can focus on fragment math and uniforms without introducing vertex buffers yet.

@vertex
fn vs_main(@builtin(vertex_index) id: u32)
  -> VertexOutput

@fragment
fn fs_main(input: VertexOutput)
  -> @location(0) vec4<f32>
